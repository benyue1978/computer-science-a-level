12 软件开发 Software Development

中文知识点提要 · Cambridge 9618 · 2027–2029 考纲

12.1 Program Development Life cycle

练习本知识点 →

阶段产物与目的
Analysis调查需求、输入输出、约束、成功标准，明确要解决的问题
Design数据结构、模块接口、算法、界面及测试计划
Coding按设计实现，并进行局部检查
Testing对照预期结果找缺陷，修复后重测
Maintenance部署后修错、适应环境或改进功能

Waterfall 顺序阶段、文档和基线明确，适合稳定需求；后期变更成本大、用户较晚看到完整系统。Iterative 反复设计实现测试并根据反馈改进，适合逐步澄清需求，但需控制范围、架构和重复工作。RAD 使用原型、工具、复用和频繁用户反馈缩短周期；需要用户投入，时间压力可能牺牲文档或长远结构。

12.2 Program Design

练习本知识点 →

Structure chart 展示模块调用层级及数据/控制参数传递：上层“处理订单”可调用“读取订单”“计算金额”“保存结果”。它表达模块关系，不是逐条执行的 flowchart。需能标明参数方向、选择和重复符号，并据此写出调用与子程序。

State-transition diagram 描述状态、事件、条件和转移。例：登录系统处于 LoggedOut；有效凭证→LoggedIn；登出→LoggedOut；多次失败→Locked。状态应是持续条件，转移应有触发事件；列出不合法事件如何处理。

12.3 Program Testing and Maintenance

练习本知识点 →

Syntax error 违反语言语法；logic error 能运行但算法结果错误；run-time error 在执行时出现，如除零、越界、文件不存在。用 trace、断点、变量观察和有针对性的测试定位，不能靠“编译通过”判断正确。

方法关注点
Dry run人工逐步模拟并填 trace table
Walkthrough与他人逐段解释设计/代码，寻找遗漏
White-box根据内部路径、分支和循环选择测试
Black-box依据规格设计输入输出，不依赖内部实现
Integration检查模块交互、接口与数据传递
Alpha开发方控制环境下的早期整体测试
Beta较广的实际用户环境反馈
Acceptance用户/客户按成功标准决定是否接收
Stub用简单替代模块模拟尚未完成的调用结果

Test strategy 定义总体方法、范围和通过标准；test plan 列测试编号、目的、输入、预期、实际结果及通过状态。先写预期结果，再运行；保留证据。

边界例子

年龄合法范围 1–120（整数）：

输入类别/预期
35Normal，接受
1、120Extreme 合法极端，接受
0、121边界外，拒绝
−10、abc、空输入Abnormal，拒绝或按规格处理

Boundary 测试通常覆盖界限本身及相邻值，不能只测合法极端。还应测试零项/一项/多项、重复值、查无结果、文件为空等与程序相关的情况。

Maintenance：corrective 修已发现错误；adaptive 适应新 OS/法规/设备等环境；perfective 改进功能、性能或易用性。修改现有程序后需验证旧功能与新功能，避免回归。

自测与易错点

1. 需求经常变化且用户能频繁参与时，比较 waterfall 与 iterative 的适配性。

2. 为“最多三次登录尝试”设计成功、失败、锁定边界测试。

3. 区分结构图、流程图、状态图分别回答“模块关系、执行步骤、状态转移”。
